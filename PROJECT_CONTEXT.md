## How to run
- Create local settings: `cp .env.example .env`, then set `JWT_SECRET_KEY` (generate with `openssl rand -hex 32`) and `SEC_USER_AGENT` (`FinCopilot your.name@example.com`, a real contact email). The app and the tests will not start without them. After changing `.env`, run `docker compose up -d` so the containers pick it up
- Start services: `docker compose up --build` (db, redis, api on port 8000, worker, beat; add `-d` to run in the background)
- Run migrations: `docker compose exec api alembic upgrade head` (roll back one step: `docker compose exec api alembic downgrade -1`)
- Open the UI: http://localhost:8000/ (redirects to http://localhost:8000/app/, the login page). Register a new organization there, or log in with an existing account. Frontend files are served straight from `frontend/`, so edits show after a browser reload (a hard reload or DevTools "Disable cache" if an old JavaScript module is still cached)
- Check it: `curl localhost:8000/health` returns `{"status":"ok"}`; `curl localhost:8000/health/ready` checks database and Redis
- Check the worker: `docker compose exec worker celery -A app.workers.celery_app inspect ping`
- psql shell: `docker compose exec db sh -c 'psql -U $POSTGRES_USER -d $POSTGRES_DB'`
- Reset the database (deletes all data): `docker compose down -v`, then start and migrate again
- Code changes under the project folder reload the API automatically. The worker and beat do NOT reload: after changing task code, the schedule or `docker-compose.yml`, run `docker compose up -d --build` (or `docker compose restart worker beat` for code-only changes)
- Run tests: `docker compose exec api pytest` (needs the stack running and `TEST_DATABASE_URL` and `TEST_REDIS_URL` in `.env`; creates the `fincopilot_test` database on first run and reuses it afterwards; flushes Redis database 1 before every test). The full suite takes about 2.5 minutes (bcrypt)
- Rate limits and cache by hand: `docker compose exec redis redis-cli keys '*'` shows the `ratelimit:*`, `companies:*`, `company:*` and `prices:*` keys; `redis-cli ttl <key>` shows the remaining time; `redis-cli del <key>` clears one (for example your own `ratelimit:auth:<ip>` after a lockout). After changing `.env`, run `docker compose up -d api` (a plain restart does not re-read it)
- Lint: `docker compose exec api ruff check .` (add `--fix` to apply safe fixes)
- Format: `docker compose exec api ruff format .` (check only: `ruff format --check .`)
- CI: `.github/workflows/ci.yml` runs `ruff check .`, `ruff format --check .` and `pytest` on pushes to `main`/`master` and on all pull requests
- Filing ingestion by hand: `docker compose exec api python -m scripts.run_filing_ingestion` (prints the run's status and message; exits 1 if a run is already in progress). First run for the 34 companies: about 3.5 minutes, 397 filings, about 1.4 GB. A repeat run takes about 50 seconds and stores nothing. Through Celery: `docker compose exec api python -c "from app.workers.tasks import ingest_filings; print(ingest_filings.delay().id)"`, then `docker compose logs worker`. Run it after the seed, because it fills `companies.industry` and `filings`
- Financial facts ingestion by hand: `docker compose exec api python -m scripts.run_financial_ingestion` (prints the run's status and message; exits 1 if a facts run is already in progress). Real run for the 34 companies: about 31 seconds, 1486 facts, 34 raw files, 145 MB in `data/raw/sec/companyfacts`. A repeat run takes about 14 seconds and creates and updates nothing. Through Celery: `docker compose exec api python -c "from app.workers.tasks import ingest_financial_facts; print(ingest_financial_facts.delay().id)"`, then `docker compose logs worker`. Needs the companies seeded; it does not need the filings job. After changing task code or the schedule: `docker compose restart worker beat`
- Price ingestion by hand: `docker compose exec api python -m scripts.run_price_ingestion` (prints the run's status and message; exits 1 if a prices run is already in progress). The FIRST run on an empty `price_bars` table is the backfill: no separate backfill code exists. Real run for the 34 companies: about 71 seconds, 42,636 bars (1,254 per company, 2021-10-04 to 2026-10-01), 34 CSV files, 5.1 MB in `data/raw/prices`. A repeat run takes about 35 seconds, creates 0 bars and updates a few thousand `adj_close` values (see Known issues). Through Celery: `docker compose exec api python -c "from app.workers.tasks import ingest_prices; print(ingest_prices.delay().id)"`, then `docker compose logs worker`. Needs the companies seeded. After changing task code or the schedule: `docker compose restart worker beat`; after changing `requirements.txt`: `docker compose up -d --build`
- Alert evaluation by hand: `docker compose exec api python -m scripts.run_alert_evaluation` (prints the run's status and message; exits 1 if an evaluation is already in progress). It checks every active alert against the stored bars of the last 30 days and takes well under a second for a handful of alerts. It normally runs by itself: the `ingest_prices` task enqueues it as soon as it finishes. Through Celery: `docker compose exec api python -c "from app.workers.tasks import evaluate_alerts; print(evaluate_alerts.delay().id)"`, then `docker compose logs worker`. After changing task code: `docker compose restart worker beat`. To test by hand with real prices, create an alert through the API and move its `watch_from` back with SQL (`UPDATE alerts SET watch_from = CURRENT_DATE - 20 WHERE id = 1;`), otherwise nothing fires: a new alert only looks at bars from its creation day on
- Filing section check by hand (2.1): `docker compose exec api python -m scripts.inspect_filing_sections` (add `--show` to print the first and last 300 characters of each section). It parses every in-scope 10-K (`RAG_TICKERS`, `RAG_LOOKBACK_YEARS`; on 2026-10-04 that is 4 filings: AAPL FY2024 and FY2025, NVDA FY2025 and FY2026) and prints the character count per section and the parse time. Real run: both sections found in all 4, about 0.3 to 0.4 seconds per filing, 1.45 seconds in total. It writes nothing and needs no network. After changing `requirements.txt`: `docker compose up -d --build`
- Embedding by hand (2.2): `docker compose exec api python -m scripts.run_embedding` (prints the run's status, message and runtime; exits 1 if a run is in progress, if `OPENAI_API_KEY` is empty, or if no in-scope filing matches). Options: `--dry-run` (split only and print chunks, characters and estimated tokens per filing and section; no OpenAI call, writes nothing, needs no key), `--reembed` (replace the chunks of the selected filings instead of skipping filings that already have some), `--ticker AAPL` and `--filing-id 8` (narrow the in-scope filings; an id outside the scope exits 1). The key goes in `.env` (`OPENAI_API_KEY=...`), then `docker compose up -d` so the containers pick it up. The normal path is automatic: the `ingest_filings` task enqueues the `embed_filings` task when it finishes. Real numbers on 2026-10-04: dry run 11.7 seconds (the first dry run in a container downloads a 1.7 MB tiktoken file, cached in the container's `/tmp`): 440 chunks, 496,036 characters, 100,127 estimated tokens (`cl100k_base`, overlap included, so about what is embedded; `text-embedding-3-small` costs a fraction of a cent for that). First real run: 4 filings, 440 chunks, 20.8 seconds, 6 embedding requests. Repeat run: 0 chunks, 0 requests, 0.0 seconds. `--reembed --ticker AAPL --filing-id 8`: that filing's 76 chunks replaced (new ids 441-516, the other filings untouched), 3.2 seconds, 1 request. After changing `requirements.txt` run `docker compose up -d --build` in the foreground (a background build that gets killed leaves stopped `Created` containers with a hash prefix in their name that block the next `up`; remove them with `docker rm <id>`); after changing task code `docker compose restart worker beat`
- Retrieval by hand (2.3): `docker compose exec api python -m scripts.try_retrieval "question" [--ticker NVDA ...] [--section risk_factors ...] [--year-from 2026] [--year-to 2026] [--top-k 5]` prints per result the rank, ticker, fiscal year, section, chunk id, RRF score, `vector_similarity`, `vector_rank`, `text_rank` and the first 200 characters. `--samples` runs the 7 sample questions of the milestone (questions 1 to 5 have a ticker filter, question 5 also `--section mdna`, question 6 has no filter and question 7 is off-topic) and prints all of them. It writes nothing, needs `OPENAI_API_KEY` (one `embed_query` call per question, a fraction of a cent) and exits 1 without it. Since 2.5 it also reranks when `COHERE_API_KEY` is set and `RERANK_ENABLED` is true (one Cohere call per question, `rerank_score` is printed per result); `--no-rerank` shows the fused order.
- Chat by hand (2.4): `docker compose exec api python -m scripts.try_chat "question" --email you@example.com [--ticker NVDA] [--follow-up "second question"] [--keep]`. It creates a session for an EXISTING user, streams the answer to the terminal, prints the rewritten follow-up, the sources sent to the model (CITED ones marked), the cited passages, and the chat log lines (chunks retrieved / passed the threshold, and whether the answer model was called, plus one `httpx2` line per real OpenAI request). The session is deleted at the end unless `--keep`. Needs `OPENAI_API_KEY` (one embedding call and one chat call per question, one more chat call for the rewrite of a follow-up). In the UI: open http://localhost:8000/app/chat.html (nav link "Research chat"), press "New chat", pick a company or All, and ask
- Evaluation by hand (2.5): `docker compose exec api python -m evals.run_eval --name <run name> [--no-rerank] [--rerank-model rerank-v4.0-pro] [--answers] [--limit N] [--rerank-pause SECONDS] [--validate-only]`. It reads `evals/questions.json` (40 questions), validates it first (structure, and every phrase must exist in the stored chunks of its ticker and section; `--validate-only` stops there, free, no keys needed), runs every question through `chat.prepare_context` (the same retrieval and threshold as chat), prints one line per question, writes `evals/runs/<name>.json` (settings, per-question results, metrics, call counts) and prints one markdown table row and the call counts. It refuses to start without `OPENAI_API_KEY`, or without `COHERE_API_KEY` unless `--no-rerank`. Real numbers on 2026-10-04: `baseline_1500` (`--no-rerank --answers`) took 2 minutes 19 seconds (40 embedding calls, 39 answer calls, 39 judge calls); a rerank run waits `--rerank-pause` (default 6.5 s, for the Cohere TRIAL limit of 10 calls a minute) after every question, so it takes at least 4.3 minutes (40 embedding and 40 rerank calls, plus 39 answer and 39 judge calls with `--answers`). A question whose rerank failed open is retried once after 30 seconds, then the run stops (it would silently be a run without rerank). Results and the chosen defaults: `evals/results.md`. Comparing chunk sizes: `docker compose exec -e CHUNK_SIZE=800 -e CHUNK_OVERLAP=100 api python -m scripts.run_embedding --reembed`, run the evaluation, then `--reembed` again without the variables (about 22 seconds each, 881 or 440 chunks)
- Agent tools by hand (3.1): `docker compose exec api python -m scripts.try_agent_tools --email you@example.com <tool> ['{"json": "arguments"}']` calls one of the five read-only tools exactly as the graph will (`tool.invoke(args, config={"configurable": {"org_id", "user_id"}})`) and prints the JSON, its size in characters and an estimated token count (tiktoken `cl100k_base`). `--samples` runs nine calls: each tool, plus NVDA `revenue_growth_pct`, AAPL `max_drawdown_pct`, all nine NVDA metrics and `compare_companies` on `net_margin_pct`. `--no-context` calls without `org_id` and `user_id` (shows the `ValueError`). `--email` must be an EXISTING user; nothing is created or written. A tool error comes back as the message the model would see. Real numbers on 2026-10-04: `--samples` took 5.9 seconds in total (the search call 5.7 seconds, every other call 0.01 to 0.04 seconds) and made ONE OpenAI embedding request and ONE Cohere rerank request, because only `search_filings` calls an external service (with an empty `COHERE_API_KEY` there is no Cohere call); a banana-bread search is one embedding and one rerank request too (3.7 seconds). The largest output was 7,031 characters, about 1,494 tokens (the search), against the 16,000-character bound. After changing `requirements.txt`: `docker compose up -d --build` in the foreground
- Seed / backfill commands: `docker compose exec api python -m scripts.seed_companies` (downloads the SEC ticker file and loads the 34 tickers listed in the script; safe to run repeatedly. Exits with status 1 and writes nothing if a ticker is missing from the SEC data or two tickers share a CIK)
- Seeded tickers (the `TICKERS` list in `scripts/seed_companies.py`): AAPL, MSFT, GOOGL, AMZN, NVDA, META, TSLA, AMD, INTC, ORCL, CRM, ADBE, JPM, BAC, GS, MS, WFC, V, MA, JNJ, PFE, UNH, LLY, MRK, XOM, CVX, WMT, KO, PEP, MCD, NKE, DIS, BA, CAT

## Environment variables
| Name | Purpose |
|------|---------|
| APP_NAME | Application title (FastAPI title). Default "Financial Research Copilot" |
| ENVIRONMENT | Environment name, e.g. development. Default "development" |
| LOG_LEVEL | Python logging level for our own loggers (DEBUG, INFO, WARNING, ...). Default "INFO" |
| POSTGRES_USER | Postgres user. Read only by docker compose (db container); ignored by the app |
| POSTGRES_PASSWORD | Postgres password. Read only by docker compose |
| POSTGRES_DB | Postgres database name. Read only by docker compose |
| DATABASE_URL | SQLAlchemy URL, psycopg v3 driver: `postgresql+psycopg://user:password@db:5432/dbname`. Required, no default |
| REDIS_URL | Redis URL, used as Celery broker and result backend, by `app/redis_client.py` (cache, rate limiting, readiness check): `redis://redis:6379/0`. Required, no default |
| JWT_SECRET_KEY | Secret that signs login tokens. Required, no default. Generate with `openssl rand -hex 32` |
| JWT_ALGORITHM | JWT signing algorithm. Default "HS256" |
| ACCESS_TOKEN_EXPIRE_MINUTES | Lifetime of an access token in minutes. Default 60 |
| SEC_USER_AGENT | Sent as the `User-Agent` on every SEC request. Required, no default. Must identify you with a real contact email, in the form `FinCopilot your.name@example.com` |
| RAW_DATA_DIR | Folder for raw downloaded files, relative to the project root. Default `data/raw` |
| FILINGS_LOOKBACK_YEARS | Filing ingestion stores only filings filed within this many years (cutoff = today minus 365 days per year). Default 3 |
| FINANCIALS_LOOKBACK_YEARS | Financial fact ingestion stores only periods that ENDED within this many years (cutoff = today minus 365 days per year). Default 6 |
| PRICE_PROVIDER | Which `PriceProvider` implementation `get_price_provider()` returns. Only `yfinance` is supported; anything else raises `ValueError`. Default "yfinance" |
| PRICES_LOOKBACK_YEARS | Every price run fetches and re-syncs this many years of daily bars (window = today minus 365 days per year). Default 5 |
| RAG_TICKERS | Phase 2 and 3 (RAG, agent) work only on these tickers: a comma-separated string, split and uppercased where it is used (`list_scope_filing_ids`). Default "AAPL,NVDA" |
| RAG_LOOKBACK_YEARS | RAG scope only includes 10-Ks filed within this many years (cutoff = today minus 365 days per year, on `filed_on`). Default 2 |
| OPENAI_API_KEY | OpenAI key for the embeddings and the chat model. Optional, default empty: an empty key means embeddings are DISABLED (the `embed_filings` task logs a warning and returns without creating a run; `scripts.run_embedding` exits 1 unless `--dry-run`) and chat is DISABLED (`POST /chat/sessions/{id}/messages` answers 503 "Chat is disabled: OPENAI_API_KEY not set"; `scripts.try_chat` exits 1). `get_embeddings()` and `get_chat_model()` raise `ValueError` when it is empty. Never logged, never committed |
| EMBEDDING_MODEL | Embedding model name passed to `OpenAIEmbeddings` and stored in `document_chunks.embedding_model`. Default `text-embedding-3-small`. The vector size is NOT a setting: it is the constant `EMBEDDING_DIMENSIONS = 1536` in `app/models/chunks.py` |
| EMBEDDING_BATCH_SIZE | Texts per embedding API request (`OpenAIEmbeddings(chunk_size=...)`, the batch size, not the text chunk size). Default 100 |
| CHUNK_SIZE | Maximum characters per chunk for `RecursiveCharacterTextSplitter`. Default 1500 |
| CHUNK_OVERLAP | Characters repeated between neighbouring chunks of a section. Default 200 |
| RETRIEVAL_CANDIDATES_K | Chunks taken from EACH search (vector and full-text) before fusion. Default 20 |
| RETRIEVAL_TOP_K | Chunks returned by `retrieve` after fusion (the `top_k` argument overrides it). Default 5 |
| RRF_K | The constant in reciprocal rank fusion, `score = sum(1 / (RRF_K + rank))`. Default 60 (the standard value) |
| CHAT_MODEL | Chat model name passed to `ChatOpenAI`, stored in `chat_messages.model` of an answer. Default `gpt-5.4-mini` (2.4) |
| RELEVANCE_THRESHOLD | A retrieved chunk is used only when its `vector_similarity` is at least this value (never the RRF score). Default 0.30: real data had 0.095 for an off-topic question and 0.44 to 0.75 for real ones (2.4) |
| CHAT_HISTORY_MESSAGES | How many recent messages of the session the question rewrite sees. Default 6 (2.4) |
| LLM_TIMEOUT_SECONDS | Timeout of one chat model call (`ChatOpenAI(timeout=...)`, which also has `max_retries=2`). Default 60 (2.4) |
| COHERE_API_KEY | Cohere key for reranking. Optional, default empty: an empty key means reranking is OFF (`retrieve` returns the fused order, nothing fails). `llm.get_reranker()` raises `ValueError` when it is empty. Never logged, never committed (2.5) |
| RERANK_ENABLED | Master switch for reranking. Default true; reranking runs only when this is true AND `COHERE_API_KEY` is set (`retrieve(rerank=None)`; an explicit `rerank=True` or `False` overrides the setting) (2.5) |
| RERANK_MODEL | Cohere rerank model. Default `rerank-v4.0-fast` (`rerank-v4.0-pro` is compared in `evals/results.md`; both ids were confirmed with a real call) (2.5) |
| RERANK_CANDIDATES_K | How many of the best fused chunks are sent to Cohere (it returns the top k). Default 20; the larger of this and `top_k` is used (2.5) |
| RERANK_TIMEOUT_SECONDS | Timeout of one Cohere call. Default 10. The Cohere SDK default is 300 seconds and `CohereRerank` has no timeout option, so `llm.get_reranker` builds the `cohere.ClientV2` itself (2.5) |
| RATE_LIMIT_AUTH_PER_MINUTE | Max `POST /auth/login` + `POST /auth/register` requests per client IP per 60-second window (one shared counter). Default 10 |
| RATE_LIMIT_API_PER_MINUTE | Max requests per authenticated user per 60-second window on every other protected route. Default 120 |
| CACHE_TTL_SECONDS | Lifetime of cached company and price responses. Default 600 |
| TEST_DATABASE_URL | Used only by pytest (`tests/conftest.py`), not part of `Settings`. Same format as `DATABASE_URL`, but the database name must end with `_test` (`fincopilot_test`). Replaces `DATABASE_URL` during tests. Required to run tests |
| TEST_REDIS_URL | Used only by pytest, not part of `Settings`. Same format as `REDIS_URL` but it MUST use a non-zero Redis database number (`redis://redis:6379/1`; 0 is the development one). Replaces `REDIS_URL` during tests, and the tests flush this database before every test; the run aborts if the number is 0. Required to run tests |

### Error format
Every error response is `{"detail": "<string>"}`, nothing else.

| Status | When | Body `detail` |
|--------|------|---------------|
| 401 | Missing, invalid or expired token, wrong login (header `WWW-Authenticate: Bearer`) | The message, e.g. "Not authenticated" |
| 403 | Wrong role | The message, e.g. "Admin role required" |
| 404 | Missing resource, or another organization's / user's resource. Unknown route | The message, e.g. "Company not found"; "Not Found" for an unknown route |
| 405 | Wrong method on a known path | "Method Not Allowed" |
| 409 | Service-level conflict | The message, e.g. "A user with this email already exists" |
| 409 | Unique-constraint violation (SQLSTATE 23505) that got past the service checks | "This resource already exists" |
| 422 | Validation error | One string: `"<field>: <message>"` per error joined with `"; "`, e.g. "password: String should have at least 8 characters". The field is the location without its first element (body/query/path) joined with dots; empty field means just the message |
| 429 | Rate limit exceeded (header `Retry-After: N`, whole seconds, at least 1) | "Too many requests. Try again in N seconds." |
| 500 | Any unhandled exception, or an IntegrityError that is not a unique violation | "Internal server error" (the exception is only logged, with its traceback) |
| 503 | Chat asked while `OPENAI_API_KEY` is empty (only `POST /chat/sessions/{id}/messages`, before the stream starts) | "Chat is disabled: OPENAI_API_KEY not set" |

### Rate limits (Redis, fixed 60-second window)
- `POST /auth/login` and `POST /auth/register`: `RATE_LIMIT_AUTH_PER_MINUTE` (10) per client IP (`request.client.host`), one shared counter, key `ratelimit:auth:<ip>`.
- Every other protected route (users, companies, filings, financials, prices, watchlists, alerts, notifications, chat routers and `GET /auth/me`): `RATE_LIMIT_API_PER_MINUTE` (120) per authenticated user, one counter for all of them, key `ratelimit:user:<user id>`. A 401 request is not counted.
- Not limited: `/health`, `/health/ready`, `/docs`, `/openapi.json`.

### Cached endpoints (Redis, TTL `CACHE_TTL_SECONDS` = 600, no invalidation)
| Endpoint | Key |
|----------|-----|
| GET /companies | `companies:list:<search stripped and lowercased>:<page>:<page_size>` |
| GET /companies/{ticker} | `company:<UPPERCASE ticker>` |
| GET /companies/{ticker}/prices | `prices:<UPPERCASE ticker>:<days>` |

Values are the response schemas as JSON. Filings and financials are not cached. Nothing with an `org_id` or `user_id` is cached.

Missing, invalid or expired token: 401 with `WWW-Authenticate: Bearer`. Wrong role: 403 (a viewer gets 403 on every watchlist write, before the watchlist is looked up). Another organization's watchlist: 404 "Watchlist not found", identical to a missing id. Alerts and notifications are different from watchlists: they are personal, so another user's alert is a 404 even inside the same organization, and no role restriction applies.

## Background jobs
| Task | Schedule | What it does |
|------|----------|--------------|
| `ingest_filings` (`app/workers/tasks.py`) | Daily at 02:00 UTC (Celery beat, entry `ingest-filings-daily`) | Calls `services.ingestion.ingest_filings`: for every company fetches the SEC submissions, stores new 10-K/10-Q filings and downloads their main documents, and records an `ingestion_runs` row. No Celery retries. A run that is skipped because another is in progress is logged as a warning, not a failure. Since 2.2 it also enqueues `embed_filings.delay()` after the service returned normally (not when the run was skipped by a `ConflictError` or raised) |
| `ingest_financial_facts` (`app/workers/tasks.py`) | Daily at 03:00 UTC (Celery beat, entry `ingest-financial-facts-daily`), one hour after the filings job | Calls `services.financials.ingest_financial_facts`: for every company downloads the SEC company facts, stores or updates the annual 10-K values of the allowlisted concepts, and records an `ingestion_runs` row with job type `financial_facts`. No Celery retries. A run skipped because another is in progress is logged as a warning. A running filings run does not block it |
| `ingest_prices` (`app/workers/tasks.py`) | 23:00 UTC, Monday to Friday (Celery beat, entry `ingest-prices-daily`, `crontab(hour=23, minute=0, day_of_week="mon-fri")`), after the US close in both summer and winter time | Calls `services.prices.ingest_prices`: for every company fetches the full lookback window of daily bars and syncs it (insert new days, update changed values), and records an `ingestion_runs` row with job type `prices`. No Celery retries. A run skipped because another is in progress is logged as a warning. Running filings or facts runs do not block it |
| `evaluate_alerts` (`app/workers/tasks.py`) | No schedule of its own: CHAINED. The `ingest_prices` task calls `evaluate_alerts.delay()` after its service call returns normally (run status success or partial), so it runs right after the daily price job (23:00 UTC, Monday to Friday). It is NOT enqueued when the price run was skipped (ConflictError) or raised an error | Calls `services.alerts.evaluate_alerts`: for every active alert of every organization, looks at the company's stored bars of the last 30 days, creates a notification for each day on which the alert fires (skipping days that already have one), and records an `ingestion_runs` row with job type `alert_evaluation`. No Celery retries. A run skipped because another evaluation is in progress is logged as a warning |
| `embed_filings` (`app/workers/tasks.py`) | No schedule of its own: CHAINED. The `ingest_filings` task calls `embed_filings.delay()` after its service call returns normally, so it runs right after the 02:00 UTC filing check (the worker has one process, so it starts after that task finished) | If `OPENAI_API_KEY` is empty: logs the warning `embeddings disabled: OPENAI_API_KEY not set` and returns, creating no run. Otherwise calls `rag.chunking.embed_filings`: for each in-scope 10-K (`RAG_TICKERS`, `RAG_LOOKBACK_YEARS`) that has no chunks yet, parses the sections, splits them, embeds the chunks and stores them, and records an `ingestion_runs` row with job type `embed_filings` and a message such as `4 filings chunked, 0 skipped, 0 failed, 440 chunks created, 0 sections missing`. Filings that already have chunks are skipped with no API call, so a day without new filings costs nothing. No Celery retries (the next chain catches up). A run skipped because another is in progress is logged as a warning |

Docker services: `worker` runs with `--concurrency=1` (one process, so the SEC throttle is global) and `beat` sends the schedule (`--schedule /tmp/celerybeat-schedule`, git-ignored as `celerybeat-schedule*`).

## Design decisions
- The repository root is the project root (no `fin-copilot/` subfolder) — the repo was created in this directory (0.1)
- Logging is configured once with `logging.basicConfig` at the top of `app/main.py`, no separate logging module; it formats our own loggers only, and uvicorn keeps its own log format (0.1)
- Custom exceptions store their text in `.message`, and the handlers in `main.py` return `{"detail": message}` (0.1)
- `.gitignore` uses `data/raw/*` with `!data/raw/.gitkeep` so the folder stays in git while its contents are ignored (0.1)
- `app/agent/` holds the Phase 3 agent code: `tools.py` since 3.1, `graph.py` in 3.2 (0.1, updated 0.2, 1.1, 3.1)
- psycopg v3 (`postgresql+psycopg://`) is the Postgres driver, not psycopg2 (0.2)
- SQLAlchemy is used in sync mode, matching the sync route handlers (0.2)
- Tables are created only through Alembic migrations, never `Base.metadata.create_all()` (0.2)
- pgvector is enabled in the first migration (`CREATE EXTENSION IF NOT EXISTS vector`), so later migrations can use the vector column type (0.2)
- The project folder is mounted into the api and worker containers (`.:/app`) so code changes reload without rebuilding; only the API auto-reloads (0.2)
- One Docker image is shared by api and worker; each service sets its own command in `docker-compose.yml` (0.2)
- `DATABASE_URL` and `REDIS_URL` have no defaults, so URLs are never hard-coded; the app will not start without a `.env` or real environment variables (0.2)
- `/health/ready` checks the database and Redis separately and reports each, with a 2s Redis timeout so a stopped Redis returns 503 quickly (0.2)
- `SessionLocal` uses `autoflush=False, expire_on_commit=False`, so objects stay readable after the service commits and returns them (0.2)
- Tests run against a real Postgres database (`fincopilot_test`), never SQLite, because the app uses pgvector and Postgres full-text search (0.3)
- `tests/conftest.py` replaces `DATABASE_URL` with `TEST_DATABASE_URL` before importing the app, and aborts the run unless the database name ends with `_test`. The app, Alembic and the tests therefore cannot touch the development database. `TEST_DATABASE_URL` is deliberately not in `Settings` (0.3)
- The test database is created once and reused; the schema comes from `alembic upgrade head` (so migrations are tested too). Nothing is dropped between runs (0.3)
- Each test runs inside an outer transaction that is rolled back at the end; the `Session` uses `join_transaction_mode="create_savepoint"`, so service `db.commit()` calls only release a savepoint and nothing persists between tests (0.3)
- Dev dependencies (pytest, httpx, ruff) are installed in the shared Docker image, since this is a dev-only project for now. Split into separate images if the project is ever deployed (0.3)
- Ruff rules are E, F, I, B, UP. B008 is handled with `extend-immutable-calls = ["fastapi.Depends"]` instead of being disabled. `*.md` is excluded because ruff 0.16 also formats code blocks in Markdown and would rewrite `CLAUDE.md` (0.3)
- CI uses GitHub Actions service containers (`pgvector/pgvector:pg16`, `redis:7-alpine`) with throwaway credentials, and sets the environment variables at job level instead of using a `.env` file (0.3)
- Ids are integer identity columns (`GENERATED BY DEFAULT AS IDENTITY`), declared with `Identity()` on the model; a plain integer primary key would produce `SERIAL` (1.1)
- Emails are globally unique (one account per email across all organizations) and stored lowercase; the services lowercase before every lookup and insert (1.1)
- Roles are a plain string column with a named CHECK constraint (`ck_users_role`) and a matching Python `UserRole` enum, not a native Postgres enum, so adding a role is a simple constraint change (1.1)
- Passwords are hashed with the `bcrypt` library directly (no passlib). bcrypt only uses the first 72 bytes, so schemas reject longer passwords (422) instead of silently truncating them. Login also rejects over 72 bytes (422) because bcrypt would raise on it (1.1)
- Access tokens are HS256 JWTs holding only the user id (`sub`, as a string because PyJWT requires it) and an expiry. Role and organization are read from the database on every request, so a role change applies immediately (1.1)
- Unknown email and wrong password return the identical 401 "Invalid email or password", so accounts cannot be discovered (1.1)
- Cross-organization access returns 404 with the same body as a missing row, never 403 (1.1)

To add a provider: write one new `PriceProvider` subclass and add one branch in `get_price_provider()`, selected by `PRICE_PROVIDER`. The ingestion tests prove this with a fake subclass (1.6)

Splits, dividend adjustments and late corrections change old values, and a full re-sync handles all three with no special code. The first run on an empty table is therefore the backfill: there is no separate backfill code (1.6)
- `close` is split-adjusted; `adj_close` is adjusted for splits AND dividends (yfinance `auto_adjust=False`, so both columns are kept). Dividend adjustment changes old `adj_close` values whenever a company pays a dividend, which is why the whole window is re-synced. Check: NVDA on 2024-06-07 (the day before its 10-for-1 split) has close 120.888 (about 1,209 unadjusted) and adj_close 120.5443 (1.6)

An empty result therefore counts as a failure (`PriceProviderError`), and a failure on one company never stops the rest of the run. The job catches only `PriceProviderError` per company (1.6)

- Alerts are PERSONAL, unlike watchlists. A watchlist is a shared team resource (any editor changes any of them); an alert notifies one person and fires on that person's chosen level, so a colleague must not see, change or delete it. Every alert and notification query therefore filters by `org_id` AND `user_id`, and another user's alert is a 404 with the same body as a missing one, even in the same organization (1.7)
- Viewers can manage their OWN alerts (routes use `get_current_user`, not `require_editor`): the "viewers are read-only" rule protects shared organization data, and a personal alert changes none. Notifications belong to the alert's owner (1.7)
- Three alert types, evaluated on the daily CLOSE (split-adjusted), never `adj_close` (a dividend would rewrite old values and move a price level): `price_above` fires on the day the close crosses above the threshold (close > threshold and the previous bar's close <= threshold); `price_below` mirrors it (close < threshold and previous >= threshold); `daily_change_pct` fires when the absolute change versus the previous bar's close, in percent, is >= the threshold, and records the SIGNED change. The percent is a `Decimal` quantized to 4 places BEFORE the comparison, so the stored `trigger_value` is the number that fired. A previous close of 0 is skipped (1.7)
- Crossing semantics: an alert whose condition is already true when it is created stays silent until the price crosses again (documented in the route description) (1.7)
- `watch_from` is the first day an alert may fire: bars before it are never considered, so old market moves cannot fire a new or changed alert. It is the UTC date of creation (the containers run in UTC), and is reset to today when the threshold actually changes or when the alert goes from inactive to active. Deactivating, or setting a field to the value it already has, leaves it alone. The previous bar used for a crossing may be older than `watch_from`, so a crossing exactly on `watch_from` fires (1.7)
- At most one notification per alert per trading day, enforced by the unique constraint `(alert_id, trade_date)`; the job also reads the alert's already-notified dates first and skips them, so a re-run creates nothing (1.7)

- The evaluation is chained from the price task with `.delay()` instead of having its own schedule: it needs the new bars, and with `--concurrency=1` it starts only after the price task has finished. It is enqueued only when the price service returned normally (success or partial), not when the run was skipped or raised. If a chain is lost, the next day's run catches up (1.7)

- Rate limiting is a fixed 60-second window in Redis: ONE pipeline (MULTI/EXEC) with `INCR`, `EXPIRE ... NX` (sets the expiry only when none exists, so later requests do not extend the window; needs Redis 7) and `TTL`. Trade-off: a client can send up to 2x the limit across a window boundary. The 429 carries `Retry-After` from the key's remaining TTL (at least 1) (1.8)

- A section is cut with start and end heading regexes (`SECTIONS`) run on the converted text. A heading sits ALONE on its line, so every pattern is anchored with `^` and `$` and includes the title: that rejects cross-references inside a sentence (even ones that wrap to the start of a line, like `Item 1A of this Form 10-K`) and the table-of-contents rows (their `|` breaks the end-of-line anchor). `Item 7` cannot match `Item 7A` because the title must follow. Patterns tolerate the real quirks: Item 7 wraps over two lines (`\s+`), html2text writes `Item 8\.` (`\\?\.`), NVDA's TOC has `Item 1C` without a period, and a non-breaking space after "Item" (`\s` matches it) (2.1)
- Longest-candidate rule: every start match is a candidate that runs to the first end heading after it; the longest candidate wins (this is what skips a table of contents written as plain lines), and it is rejected when shorter than `MIN_SECTION_CHARS` (2000). On the 4 real filings there is exactly one start match per section, so the rule is only exercised by the inline tests (2.1)
- The heading itself is excluded from the content, and the content is stripped. Risk Factors ends at Item 1B, 1C or 2; MD&A ends at Item 7A or 8 (2.1)
- Each Document's metadata is exactly `{company_id, ticker, filing_id, form_type, fiscal_year, section}`, plain JSON types (`fiscal_year` is None only when the filing has none) (2.1)
- A missing or too short section is a warning (ticker, accession number, section, reason: start heading not found, end heading not found, or too short), not an error; `load_filing_sections` returns the sections it found. A wrong input is an error: unknown filing id is `NotFoundError`, a non-10-K or a filing without a downloaded document is `ValueError` (2.1)
- 10-K only. 10-Qs have different items and are out of scope (2.1)
- `load_filing_sections` is read-only: it writes nothing to the database or `data/raw` and makes no network calls (tested by blocking sockets during the inspection) (2.1)
- 2.2 models: embeddings are OpenAI `text-embedding-3-small` through LangChain's `OpenAIEmbeddings` (1536 dimensions). The chat model is OpenAI `gpt-5.4-mini`, used from 2.4: nothing was built for it in 2.2 and there is no chat setting yet. The reranker is STILL OPEN and is chosen in 2.5 (2.2)
- The vector size is the constant `EMBEDDING_DIMENSIONS = 1536` in `app/models/chunks.py`, not an environment setting: the column type is `vector(1536)`, so changing it needs a migration and a re-embed of everything, and an environment variable would only let the two drift apart. `embed_filings` checks every vector's length before inserting, so a wrong `EMBEDDING_MODEL` fails with "Embedding has N dimensions but the table expects 1536: check EMBEDDING_MODEL" instead of a database error. `dimensions` is deliberately not passed to `OpenAIEmbeddings`, so the check can notice a model with another size (2.2)
- Chunks are `CHUNK_SIZE` 1500 characters with `CHUNK_OVERLAP` 200, measured in characters (the splitter's `len`). Real result: median 1,264 characters and 243 tokens, maximum 579 tokens (the model accepts 8,191): about one or two paragraphs, small enough that one chunk is about one topic, large enough to keep a risk factor's heading with its text. The 200-character overlap (about 13 percent) repeats the end of a bullet list or paragraph so a sentence cut at a boundary is whole in one of the two chunks. Both are settings, because they are meant to be compared in 2.5 (2.2)
- Splitting happens inside each section only: `split_documents` is called on the section Documents, so a chunk never mixes Risk Factors and MD&A and every chunk's `section`, `company_id` and `fiscal_year` are exact. `RecursiveCharacterTextSplitter` cuts on blank lines first, then lines, then spaces (its defaults), and copies the section's metadata to each chunk (2.2)
- `OpenAIEmbeddings` is created with `check_embedding_ctx_length=False`: by default it tokenizes every text with tiktoken and sends token arrays, which makes the worker download a 1.7 MB encoding file on first use (42 seconds here, lost when the container is rebuilt) and needs a second outbound host. Our chunks are at most about 600 tokens against a limit of 8,191, so the check protects nothing; plain text is sent and OpenAI tokenizes it. Batches are the same: `EMBEDDING_BATCH_SIZE` texts per request. tiktoken is used only by the dry run (2.2)
- Idempotency is "skip a filing that already has chunks" (`has_chunks`), checked BEFORE parsing and embedding, so a repeat run makes no API call at all (proved: 0 requests on the second real run). The unique constraint on `(filing_id, section, chunk_index)` is the backstop. The skip is per filing, not per chunk or per section (2.2)
- Replace (`--reembed`, `replace=True`) works per filing in ONE transaction: parse, split and embed first (nothing is written yet), then delete the filing's old chunks, insert the new ones and commit. An OpenAI error, a wrong dimension or a parse error therefore leaves the old chunks untouched, and a database error rolls the delete back. Replacing gives the rows NEW ids (tested) (2.2)
- No vector (HNSW or IVFFlat) index: the table holds 440 rows, an exact scan is fast and has perfect recall, and an approximate index would only add recall loss and build cost. Revisit when the table has many thousands of rows. The GIN index on `search_vector` is created because it costs nothing and 2.3 needs full-text search (2.2)
- `search_vector` is a generated column (`GENERATED ALWAYS AS (to_tsvector('english', content)) STORED`), so Postgres keeps it in sync with `content` and no code ever writes it. It uses the `english` configuration (stemming and stop words), which is right for English filings; a query must use the same configuration (`plainto_tsquery('english', ...)`) (2.2)
- There is no separate index on `filing_id`: the unique constraint's index starts with `filing_id`, so `has_chunks` and `delete_by_filing` already use it. `company_id` has no index either (a few hundred rows) (2.2)
- `embed_filings` runs after `ingest_filings` through a chained `.delay()` (the same pattern as prices to alerts in 1.7) and has no beat entry: new filings are embedded right after they are stored, and the worker's single process makes it start after the filing task ends. It is enqueued only when the filings service returned normally. This is a small change to a Phase 1 task (2.2)
- An empty `OPENAI_API_KEY` means "embeddings disabled", not "failed": the task logs a warning and returns WITHOUT creating an `ingestion_runs` row (no failed row every night on a machine without a key), and the script exits 1 with the same message. The app and the tests start without a key (2.2)
- Per-filing errors are counted as failed and the other filings continue; the run is `partial` when any failed. The caught types are `openai.OpenAIError`, `ValueError`, `OSError` and also `RuntimeError`, because LangChain's `TextLoader` turns a missing or unreadable file into a `RuntimeError` (checked: cause `FileNotFoundError`), which would otherwise fail the whole run. A filing in which NO section is found counts as failed (with a log line), so it is visible instead of being silently re-parsed every day. The single broad `except Exception` only calls `fail_run`, logs and re-raises, as in the Phase 1 jobs. An OpenAI error is logged by class name only, because its message can contain part of the API key (2.2)
- The run's overlap-guard label is "filing embedding" ("A filing embedding ingestion run is already in progress"). `finish_run` writes `N filings chunked, N skipped, N failed, N chunks created, N sections missing`; "sections missing" is `len(SECTIONS)` minus the sections found, summed over the processed filings (2.2)
- `scripts/run_embedding.py` only works inside the RAG scope: `--ticker` and `--filing-id` narrow `list_scope_filing_ids`, they never widen it, so the script cannot spend money on an out-of-scope filing. `embed_filings` itself trusts an explicit `filing_ids` list (used by the script and the tests) (2.2)
- Every test gets fake embeddings: an autouse fixture in `conftest.py` replaces `app.rag.llm.get_embeddings`, which is why `chunking.py` calls it as `llm.get_embeddings()` (module attribute) and not through a `from` import. The fake has 1536 dimensions like the real model (2.2)

- 2.3 retrieval is HYBRID: a pgvector similarity search and a Postgres full-text search (each returns `RETRIEVAL_CANDIDATES_K` = 20 candidates), merged with reciprocal rank fusion, `score = sum(1 / (RRF_K + rank))` over the lists a chunk is in, rank starting at 1, `RRF_K` = 60 (the standard constant). RRF uses only ranks, so the two scales (cosine distance, `ts_rank_cd`) never have to be compared. Then `RETRIEVAL_TOP_K` = 5 chunks are kept. A chunk found by both searches always outranks one found by a single search of similar rank (2.3)
- The full-text query is an OR query: the question's `\w+` words joined with ` or ` and passed to `websearch_to_tsquery('english', ...)`. A question is a natural sentence, and an AND query (`plainto_tsquery`) needs every word in one chunk: on the real data it matched 0 chunks for two sample questions where the OR form matched 191 and 112. `websearch_to_tsquery` never raises on user input and the `english` configuration drops stop words; extracting `\w+` first removes quotes, a leading `-` and apostrophes, which that function would read as operators. The word `or` inside a question is harmless (checked). A question without any word skips the full-text search (2.3)
- The full-text rank is `ts_rank_cd` (cover density, rewards matched terms that are close together), and every query orders by `rank DESC, id`, because it gives coarse values with many ties (1.8, 1.7, 1.6...). The vector query orders by `distance, id` (2.3)
- Similarity is cosine distance (the `<=>` operator, `Vector.comparator.cosine_distance`) with no vector index, an exact scan over 440 rows (see the 2.2 decision). `vector_similarity` is `1 - cosine_distance` (2.3)
- Every returned chunk carries `vector_similarity`, also chunks that only the full-text search found (one extra query, `get_distances`, for the kept chunks missing from the vector list). It is the signal 2.4 will compare with its relevance threshold, NOT the RRF `score`: an RRF score only depends on ranks (the best possible value is about 0.0328 for any question, even an off-topic one), so it has no absolute meaning, while cosine similarity does (2.3)
- Ties in the fused score are broken by `chunk_id`, so the order is deterministic (tested with both list orders) (2.3)
- An unknown ticker is not an error: it matches nothing and the result is `[]`. Tickers are stripped and uppercased. An empty `tickers` or `sections` list means "no filter", like `None`. Wrong input raises `ValueError`: empty question, an unknown section, `year_from > year_to` and `top_k < 1` (the last one was added to the spec) (2.3)
- Fusion is plain Python, not LangChain: `EnsembleRetriever` lives only in `langchain-classic` (forbidden by `CLAUDE.md`; checked in the installed packages, `langchain-core` has no fusion code) and a `BaseRetriever` subclass around our SQL would be a custom Runnable class (also forbidden). RRF is about ten lines in `retrieve`. LangChain is used for `embed_query` and the `Document` output (2.3)
- Only one helper was added (`apply_filters` in the repository, used by both searches, as `CLAUDE.md` 3.2 allows). The RRF is not a separate function: the tests replace the two repository searches with fixed ranked lists to check the arithmetic. Retrieval writes nothing, needs no `org_id` (shared public data) and adds no table, endpoint or LLM call (2.3)
- 2.4 chat model: OpenAI `gpt-5.4-mini` through LangChain's `ChatOpenAI(model, api_key, timeout=LLM_TIMEOUT_SECONDS, max_retries=2)`, created only in `llm.get_chat_model()`. No `temperature`: LangChain's validator drops any value other than 1 for non-chat `gpt-5*` models, so it could not make answers more deterministic anyway (answers vary between runs). No `reasoning_effort`: the one real call (a streamed "ok", 13 input and 4 output tokens, 2.9 seconds) used 0 reasoning tokens by default, so tuning it is left to the 2.5 evaluation. `.stream()` yields `AIMessageChunk`s with string content; the first and last pieces are EMPTY strings, so chat skips empty pieces and never sends an empty token event. It reads `piece.text` (also right for block content) (2.4)
- 2.4 flow order (written out in `ask`, plain and sequential): load the session, get the model, load the last `CHAT_HISTORY_MESSAGES` messages, rewrite (only with history), retrieve, filter by threshold, send `sources`, no-answer or numbered prompt and stream, parse markers, save in one transaction, send `done`. The follow-up rewrite (`REWRITE_PROMPT | model`, `.invoke()`) runs only when the session has history, so a first question makes no extra LLM call; an empty rewrite falls back to the original question and stores no `rewritten_question`. The answer prompt receives the STANDALONE question (2.4)
- 2.4 `ask` is an ordinary function that checks the session (404 "Chat session not found", the same body for missing, a colleague's and another organization's) and creates the model (empty key to `ServiceUnavailableError`, 503) BEFORE any response exists, then returns an inner generator that does everything else. Reason, found in the inspection: Starlette sends the 200 headers before it pulls the first item of the generator, so a check inside a real generator would arrive after the status was already sent. Failures inside the generator (OpenAI, the database, `ValueError`) are caught as `openai.OpenAIError`, `SQLAlchemyError` and `ValueError` only, roll back, are logged by CLASS NAME only (an OpenAI error message can contain part of the key) and become the `error` event with a generic text; any other exception is a bug and propagates (the browser then sees a stream that ends without `done` and shows "The answer was interrupted") (2.4)
- 2.4 session handling during the stream, from the inspection: in FastAPI 0.142.2 the `get_db` dependency exits AFTER the streaming generator finished (checked with the real `SessionLocal`), so the generator uses the request's own session, no second `SessionLocal()` is needed, and the one save at the end commits it. The cost: that session holds an open read transaction during the model calls (see Known issues) (2.4)
- 2.4 relevance threshold: `RELEVANCE_THRESHOLD` = 0.30 on `vector_similarity`, never on the RRF score (which only orders chunks and has no absolute meaning). The 2.3 real numbers were 0.095 for the off-topic question and 0.47 to 0.75 for real ones; 2.4 real data: 0.44 to 0.75 for real questions, and 0 of 5 chunks passed for banana bread. Chunks below the threshold are NOT numbered and NOT sent to the model, so the model cannot cite weak evidence, and the fixed `NO_ANSWER` text is returned with no answer LLM call (a follow-up may still have used the rewrite call). Questions that are on-topic enough to pass but unanswerable ("What will NVIDIA's stock price be next year?", similarity 0.44 to 0.54) are left to the model, which said it does not know and cited nothing (2.4)
- 2.4 prompt rules: answer only from the numbered excerpts, cite with one number per bracket (`[1][3]`), do not cite numbers that are not listed, say "don't know" when the excerpts do not contain the answer, use no outside knowledge, give no investment advice and do not predict prices. The first real answer put a single `[2][3]` at the END of a multi-sentence answer, so the rule was tightened to "put the citation right after the sentence it supports"; only that one question was rerun with the new wording (it then had a marker after each sentence); the other real answers already had per-sentence markers, but this is a prompt, not a guarantee. Excerpts are labelled `[1] NVDA FY2026 10-K, Risk Factors:` (`SECTION_NAMES` gives the short section names) (2.4)
- 2.4 chat retrieval is restricted to the exact RAG scope: `retrieve` got an optional `filing_ids` filter (an empty list means "no filter", like the others) and chat passes `list_scope_filing_ids(db)`. Because an empty list would then search EVERYTHING, chat answers `NO_ANSWER` without calling `retrieve` when the scope is empty (tested). This closes the 2.3 issue about chunks of filings that left the window, for chat; `scripts.try_retrieval` still searches without it (2.4)
- 2.4 streaming format is NDJSON (`application/x-ndjson`, one JSON object per line), not Server-Sent Events: the request is a POST with a JSON body and a bearer token, `EventSource` can do neither, and `fetch` with `getReader()` is enough. Events: `sources`, `token`, `done`, `error` (full format under API endpoints). Checked with the server: each line is flushed as it is yielded (chunked transfer, no buffering), and `json.dumps` escapes non-ASCII so a character is never split between network chunks. The real model splits markers across pieces (`"["`, `"2"`, `"]["`), which is why markers are parsed from the complete answer, never from pieces (2.4)
- 2.4 persistence: the user message, the assistant message, the citations, the title (first question stripped and cut to 100 characters, only when the session has none) and `updated_at` are saved in ONE transaction AFTER the stream, so a failure at any point leaves nothing behind. An empty model answer is treated as a failure. Markers `[n]` and `[1, 2]` are parsed with a regex on the full text; numbers outside 1..n are ignored and each distinct valid number gets one citation row (`[1][1][3]` with 2 sources stores only 1). `chat_messages.model` is stored on answers (null for the fixed "I don't know"); the number of chunks given to the model is only logged, there is no `chunk_ids_used` column (2.4)
- 2.4 citations survive re-embedding: `citations.chunk_id` is a nullable FK with `ON DELETE SET NULL` and each citation stores a snapshot (`filing_id`, `ticker`, `fiscal_year`, `section`, `content`). Verified on real data: after `run_embedding --reembed --filing-id 295` the citation of a replaced chunk had `chunk_id` null and byte-identical content, while a citation of an untouched filing kept its `chunk_id`. `--reembed` itself was not changed. The UI says when a passage is a stored copy (`chunk_id` null). `filing_id` in the snapshot is a plain number, not a foreign key (2.4)
- 2.4 chats are PERSONAL, like alerts: every session query filters by `org_id` AND `user_id`; messages and citations have no `org_id` and are only read through a session loaded that way (the `watchlist_items` pattern). Every role, including viewer, can create chats and ask: a chat changes no shared organization data. Session create and delete write the audit rows `chat_session.create` and `chat_session.delete` (entity id = session id); messages write none. The router is included with `limit_user`; one question counts as one request (2.4)
- 2.4 frontend: `common.js` has nine exports, the ninth is `apiStream(path, body, onEvent)`. It repeats the token header and the 401 handling of `api()` (about 15 lines) instead of sharing a helper, so the working `api()` used by seven pages was not touched. After the stream ends the page loads the conversation again from the server (the loader re-renders, no extra render helper), so answers always show what is stored and the `[n]` buttons are built from the stored citations; the `sources` event only drives the status line. A failed question is not saved, so its text is put back in the input box. A chat is opened by a "New chat" button that creates the session and loads `chat.html?id=`, the same pattern as `watchlists.html?id=` (2.4)
- 2.4 tests never reach OpenAI: the autouse `fake_chat_model` makes the chat model FAIL the test when it is called, and tests that expect answers install `ScriptedChatModel` (a `GenericFakeChatModel` subclass with a call recorder) through `script_chat`. `chat.py` calls `llm.get_chat_model()` through the module so tests can replace it. A question equal to a chunk's text has similarity 1 with it and about 0 with the others (fake embeddings), so the 0.30 threshold is tested without patching it (2.4)
- 2.5 reranker: Cohere through LangChain's `CohereRerank` (`langchain-cohere` 0.6.0), default `rerank-v4.0-fast`; `rerank-v4.0-pro` is the compared alternative. Both ids were confirmed with one real call each (3 short documents; scores 0.85 / 0.16 / 0.11 for fast and 0.95 / 0.37 / 0.19 for pro, the foundry sentence first in both). Numbers that chose it (`evals/results.md`, 33 answerable questions, chunk size 1500): without rerank hit@1/3/5 0.515 / 0.758 / 0.848 and MRR@5 0.642; fast 0.636 / 0.939 / 1.000 and 0.788; pro 0.697 / 0.909 / 1.000 and 0.816. Fast and pro differ by at most 2 questions in any metric (noise), so the lighter and cheaper fast model is the default; reranking itself is worth 4 to 6 questions in hit@5 (2.5)
- 2.5 candidates and `top_n`: after the RRF step the best `max(top_k, RERANK_CANDIDATES_K)` fused chunks (20 by default; with 20 candidates per search the fused list has up to 40) are built as Documents with all the old metadata and sent to `llm.get_reranker(top_n=top_k).compress_documents(documents, question)`; the order it returns is the result. `vector_similarity` is therefore computed for all candidates, not only the final top k (the step that fills it for text-only chunks runs on the larger set). `CohereRerank` returns copies with `metadata["relevance_score"]`; `retrieve` moves it to `rerank_score` so no extra key appears. No `ContextualCompressionRetriever` or other `langchain-classic` class: `compress_documents` is called directly. The candidate count and `top_k` were not tuned (2.5)
- 2.5 fail open: when the Cohere call raises `cohere.core.ApiError` (every HTTP error: 401, 429, 5xx) or `httpx.HTTPError` (timeouts and connection errors; checked with a real refused connection) `retrieve` logs a warning with the CLASS NAME only (never the message or the key) and returns the fused top k with `rerank_score` None; any other exception propagates. Same reasoning as the Redis fail-open in 1.8: chat keeps working when Cohere is down. `cohere.ClientV2` is built in `llm.get_reranker` with `timeout=RERANK_TIMEOUT_SECONDS` (10) because `CohereRerank` has no timeout option and the SDK default is 300 seconds, which would make a Cohere outage hang chat for 5 minutes; this is why `cohere` is imported and pinned directly. No document truncation option is passed (`CohereRerank` has none; chunks are at most about 400 tokens against Cohere's 4000-token default) (2.5)
- 2.5 the threshold stays on `vector_similarity`: the rerank score has another scale than cosine similarity and changes between model versions (real: the off-topic banana-bread question still gets rerank scores of 0.35 and 0.34 for its two nearest chunks, which are page-footer fragments, while its cosine similarity is 0.095). Chunks below 0.30 are neither numbered nor sent to the model, whatever their rerank score; tested with a reranker that puts irrelevant chunks first. An observation from the evaluation, not applied: a threshold of about 0.42 would have rejected the two lowest on-topic unanswerable questions in every run without rejecting any answerable one (2.5)
- 2.5 `prepare_context(db, question, ticker) -> (retrieved, passing, sources, context_text)` is the one helper added to `chat.py`: the same logic is used by `ask` and by the evaluation (CLAUDE.md 3.2: two places). It returns four values instead of the planned two because `ask` needs the passing Documents' `filing_id` for the citation snapshot (the streamed `sources` must not change), and the evaluation needs the pre-threshold Documents (best similarity, hit@k); with two values the evaluation would have called `retrieve` twice per question (double the embedding and Cohere calls, and with reranking possibly different results). `ask` keeps its order and behaviour; the 2.4 tests pass unchanged (2.5)
- 2.5 phrase-based labels: a retrieved chunk is relevant when its ticker and section match an expected entry and its text contains one of the entry's phrases (case-insensitive, whitespace collapsed because the filings are hard-wrapped). Chunk ids are not used because they change on every re-embed and every chunk-size change, while a distinctive phrase from the filing survives both. The evaluation refuses to start unless EVERY phrase exists in at least one stored chunk of its ticker and section; before the paid runs all phrases were also checked against an offline 800/100 split, so the chunk-size comparison measures retrieval and not label breakage. The labels under-count (a relevant chunk worded differently is not found) (2.5)
- 2.5 evaluation design: each question runs through `chat.prepare_context`. Retrieval metrics (hit@1/3/5, MRR@5) are computed over the 33 answerable questions on the top 5 `retrieve` returns BEFORE the threshold; rejection metrics use the threshold (and, with `--answers`, the model's abstention). Answers are generated exactly as chat does (same context text, same `QA_PROMPT`, `.invoke()`); below the threshold the answer is the fixed `NO_ANSWER` (no model call) and counts as an abstention. The judge is `JUDGE_PROMPT | get_chat_model().with_structured_output(JudgeResult)`: it splits the answer into claims, gives each claim's cited numbers and `supported` (a cited excerpt states it; a claim without a citation is NOT supported) and an `abstained` flag. Faithfulness and citation coverage are averaged per answer over answerable, non-abstained answers; coverage counts a valid number (1 to the number of excerpts) and is computed in code, not by the judge. The same model answers and judges: a known bias. Run settings are read back from the stored chunks (longest chunk rounded up to 100, longest overlap), because the settings used at embedding time are not stored. A rerank that fails open during a run is retried once after 30 seconds, then the run stops, because it would silently be a no-rerank run (2.5)
- 2.5 chunk size: 800/100 was tried against 1500/200 (all 4 filings re-embedded, 881 chunks, then back to 1500/200, 440 chunks). 1500 wins both without rerank (hit@5 0.848 against 0.667, MRR@5 0.642 against 0.507) and with `rerank-v4.0-fast` (hit@5 1.000 against 0.879, MRR@5 0.788 against 0.713). Final defaults: `CHUNK_SIZE` 1500, `CHUNK_OVERLAP` 200, `RERANK_MODEL` `rerank-v4.0-fast`; the stored chunks match (440: AAPL FY2024 76, FY2025 83, NVDA FY2025 142, FY2026 139, new ids). The citations table was EMPTY during the evaluation, so the two re-embeds nulled no citation `chunk_id` (with citations present they would be null with the snapshot intact, the 2.4 design) (2.5)
- 2.5 tests: the autouse fixture `no_reranker` empties `COHERE_API_KEY` and makes `llm.get_reranker` fail the test when called, so no test can reach Cohere and a developer's real key cannot switch reranking on elsewhere; rerank tests install a small scripted `FakeReranker` with `compress_documents`. Retrieval calls `llm.get_reranker(...)` through the module so tests can replace it. One 2.3 test changed: the exact metadata key set in `test_metadata_has_exactly_the_documented_keys_and_values` gained `rerank_score` (the key is always present, None without reranking); nothing else in the 2.3 and 2.4 tests changed (2.5)
- 2.5 trial key: the Cohere key is a trial key (10 rerank calls a minute, 1,000 API calls a month, per Cohere's rate-limit page), so the evaluation waits 6.5 seconds after each question when reranking (`--rerank-pause`, set 0 for a production key). The whole milestone used 131 Cohere calls (120 in the three rerank runs, 11 in the inspection and manual checks) (2.5)

- 3.1 the five tools return bounded JSON because their output goes into the model's context on every call, in every step of a run: `search_filings` at most 8 passages of at most 1,500 characters, `get_financials` at most 9 metrics x 10 years of four fields, `get_price_history` a summary plus at most 30 sampled points (never all bars), `compute_metrics` at most 9 points, `compare_companies` at most 5 companies x 9 points. The bound for every tool is 16,000 characters (about 4,000 tokens), asserted by tests at the largest arguments (the largest real sample output was 7,031 characters, the search). `get_financials` drops `accession_number`, `filed_on` and `period_start` from each point (the model does not need them; the full NVDA answer went from 11,780 to 5,575 characters) (3.1)
- 3.1 `org_id` and `user_id` reach a tool only through `config["configurable"]` (a `config: RunnableConfig` parameter that LangChain hides from the model's schema, checked in the JSON schema), never as tool arguments, so the model cannot choose whose data it acts on. A missing value is a `ValueError` (a bug of the graph, not a model mistake). Verified through a real `ToolNode`: the values arrive unchanged (3.1)
- 3.1 all five tools wrap SHARED public data (filings, financials, prices), so no query is filtered by `org_id`. The context is still mandatory, so a tool can only run inside an authenticated run, and the private tools of 3.3 (`create_alert`, `save_report`) follow the same pattern with real filters. The tools call SERVICE functions (and `retrieve`), never repositories. Every call logs one line with `org_id` and `user_id` (3.1)
- 3.1 each tool opens its own short session (`with SessionLocal() as db:`) and closes it before returning. An agent run lasts minutes and calls the model many times; a session shared through the graph would sit "idle in transaction" the whole time (the known 2.4 issue). Tools never get a session through the graph or the config. Tests replace `app.agent.tools.SessionLocal` with a context manager that yields the test session and does not close it (3.1)
- 3.1 errors: expected problems the model can fix or report (out-of-scope ticker, no data, a metric that cannot be computed, search disabled, a blank query) are a `ToolException` with a short plain message; bugs (a missing context, any unexpected exception) propagate. Inspection of langgraph 1.2.12 showed that the default `ToolNode` turns invalid ARGUMENTS (for example `days=99999`) into an error message but lets a `ToolException` PROPAGATE, which would crash the run. So every tool has `handle_tool_error = True` (set in a two-line loop below `READ_ONLY_TOOLS`; the `@tool` decorator does not accept it in this version): the exception text becomes the tool's output (an error `ToolMessage` with exactly that text), a `ValueError` still propagates, and no `ToolNode` built in 3.2 or 3.3 can forget a handler. Consequence: a direct `tool.invoke(...)` returns the message as a string instead of raising; `tool.func(...)` raises. An OpenAI error while embedding is logged by CLASS NAME only and becomes "Filing search failed. Try again." (its message can contain part of the key) (3.1)
- 3.1 a `ToolNode` cannot be invoked on its own in langgraph 1.2.12 (`ValueError: Missing required config key 'N/A'`: it needs the `Runtime` that a compiled graph supplies), so the tests run each tool through the smallest possible graph, `StateGraph(MessagesState)` with the `ToolNode` and one edge from START, invoked with a hand-built `AIMessage`. No model, no routing, no loop (3.1)
- 3.1 scope: the tools work only on `RAG_TICKERS` (AAPL, NVDA), split, stripped and uppercased where used (`check_ticker`); lowercase or padded input for an allowed ticker works, and any other ticker is rejected with an error that lists the available tickers. A ticker in scope but without a company row is "No data stored for X" (3.1)
- 3.1 `search_filings` reuses `retrieve` with `filing_ids=list_scope_filing_ids(db)`, the sections and fiscal-year filters, and keeps only chunks with `vector_similarity >= RELEVANCE_THRESHOLD` (never the rerank or RRF score, the chat rule). Reranking follows the settings (`rerank=None`) and fails open as before. `chat.prepare_context` was NOT reused: it has no section or year filter, takes one ticker and builds the numbered chat prompt; the tool's few lines are cheaper than widening it. An empty scope skips `retrieve` (an empty `filing_ids` list means "no filter"). "Nothing relevant" is a normal result (`{"results": [], "message": ...}`), not an error. `top_k` is 1 to 8 (default `RETRIEVAL_TOP_K`), every result has its `chunk_id` so 3.2 and 3.4 can cite it. The text is quoted filing text and is NOT sanitized (3.1)
- 3.1 derived metrics are computed in plain Python from `DERIVED_METRICS` (the single source of truth: key, label, unit, kind, inputs, formula text; a test checks that the tool signatures' `Literal`s list exactly its keys and the nine `MetricName` values). Six financial metrics per fiscal year from the stored annual values: `revenue_growth_pct` (year over year, the previous stored point must be exactly `fiscal_year - 1`, fetches `years + 1` points), `net_margin_pct`, `operating_margin_pct`, `gross_margin_pct`, `return_on_equity_pct` (net income / YEAR-END equity, no averaging), `liabilities_to_equity`; three price metrics over the last `days` days from the stored `close`: `price_return_pct`, `annualized_volatility_pct` (sample standard deviation of daily close-to-close returns x sqrt(252) x 100, at least 3 bars), `max_drawdown_pct` (largest fall from a previous peak, negative, at least 2 bars). A year with a missing input or a zero or negative denominator (negative equity, zero revenue) is left out and explained in `notes`; if nothing at all is computable the tool raises a `ToolException`. Every point carries its `inputs` so a reviewer can check the number by hand; values are rounded to 2 decimals. Simplifications: no averaging of equity, no dividends in price metrics, daily returns on stored closes only (3.1)
- 3.1 `compare_companies` runs the same `calculate_metric` once per ticker and accepts the nine base metrics too (stored values, `inputs` empty). A company that cannot be computed is listed in `notes` and the others are returned; if none works it raises. `latest` (newest point of each company, highest value first) keeps every company's own `period_end`; when two latest `period_end` dates are more than 60 days apart a note says the fiscal years are not aligned (real: AAPL 2025-09-27 against NVDA 2026-01-25, 120 days). The same ticker twice counts as one company ("Give at least 2 different tickers to compare"); fewer than 2 or more than 5 tickers is rejected by the argument schema. It gives numbers only, no advice (3.1)
- 3.1 `get_price_history` returns a summary and at most 30 evenly spaced `{date, close}` points (indexes `round(i * (n - 1) / 29)`, which always include the first and last bar), the split-adjusted `close` and not `adj_close` (the same choice as alerts and the chart; dividends are excluded), and reads through `prices.get_prices`, so the Redis cache applies (up to `CACHE_TTL_SECONDS` old) (3.1)
- 3.1 `langgraph` is added now, although the graph is built in 3.2, because the tests verify the tools through a real `ToolNode` (so 3.2 meets no surprise) and the dependency check is cheap to do once. Only `langgraph==1.2.12` is pinned; it brings `langgraph-checkpoint` 4.2.0 (which holds `InMemorySaver`), `langgraph-prebuilt` 1.1.0 (`ToolNode`), `langgraph-sdk` 0.4.5 and `ormsgpack`, and DOWNGRADES `websockets` from 17.2 to 16.1.1 (`langgraph-sdk` requires `<17`); `langchain-core` stays 1.6.6, `pip check` is clean, importing langgraph makes no network call and leaves LangSmith tracing off. No Postgres checkpointer package yet (3.2 decides). Import paths confirmed: `langgraph.graph.StateGraph`, `langgraph.prebuilt.ToolNode` and `tools_condition`, `langgraph.checkpoint.memory.InMemorySaver`, `langgraph.types.interrupt` and `Command` (3.1)
- 3.1 the three helpers are allowed by CLAUDE.md 3.2 because each is used in several places: `require_context` and `check_ticker` by all five tools, `calculate_metric` by `compute_metrics` and `compare_companies`; none calls another helper (`calculate_metric` calls services only). - Evaluation (2.5): phrase labels can miss a relevant chunk that words the idea differently, so hit rates are lower bounds; two labels are broad (c03 `licensing requirements`, n09 `AI Diffusion`); text repeated in two fiscal years counts for either. The questions and labels were written by reading the same filings the system retrieves from.
- Evaluation (2.5): retrieval metrics are computed on the top 5 before the 0.30 threshold, and "unanswerable rejected" means different things in retrieval-only runs (threshold only, 0.143) and `--answers` runs (threshold or abstention, 0.714 and 0.857); the two are not comparable.
- Chat (2.5): the threshold alone rejects only the off-topic question: the six on-topic unanswerable evaluation questions had a best similarity of 0.33 to 0.73 and passed it; the model abstained on 4 of 6 without and 5 of 6 with reranking. u02 ("What will Apple's stock price be at the end of next year?") was answered in both runs from risk-factor text about stock-price volatility, with citations (not a refusal). A threshold of about 0.42 would have separated the two lowest on-topic questions from all answerable ones, but the margin is 0.02 and it concerns two questions.
- Chat (2.5): reranking adds one network call to every chat question (about 0.7 seconds in the one real chat run: embedding at 21:21:27.230, Cohere answer at 21:21:27.947) and one more external dependency; chat works without it (fail open). A Cohere timeout costs up to `RERANK_TIMEOUT_SECONDS` (10) per question; the SDK also retries 429 and 5xx answers by itself (not measured). The `httpx` logger prints the Cohere URL, never the key.
- Cohere trial key (2.5): 10 rerank calls a minute and 1,000 API calls a month. The evaluation is paced for it (6.5 seconds per question); a production key allows `--rerank-pause 0`. The month's budget is shared by chat: each chat question uses one call when reranking is on, and a chat burst above 10 a minute would hit the limit and fall back to the fused order (fail open).
- Retrieval (2.5): reranking only reorders the best 20 fused chunks (`RERANK_CANDIDATES_K`); the candidate count, `top_k` and the threshold were not tuned. The reranker sees the raw chunk text including the parsing noise (page footers, flattened tables).
- Embeddings (2.5): `CHUNK_SIZE` and `CHUNK_OVERLAP` used at embedding time are not stored with the chunks (the evaluation reads them back as the longest chunk and the longest observed overlap). If someone re-embeds with other settings, only `--reembed` plus the evaluation's "chunk size" column shows it.

- Agent tools (3.1): `app/agent/tools.py` is about 650 lines (CLAUDE.md 3.3 says roughly 400+ is where a split can be justified). The plan estimated 380; the five tools, their long docstrings (the model reads them), `DERIVED_METRICS` and the one long `calculate_metric` account for it. It was NOT split (one module was the approved layout); a split would move `DERIVED_METRICS` and `calculate_metric` to their own module.
- Agent tools (3.1): fiscal years are not aligned between Apple (year ends late September) and NVIDIA (late January): the same `fiscal_year` is a different calendar period (real: AAPL FY2025 ends 2025-09-27, NVDA FY2026 ends 2026-01-25). The tools show `period_end`, the descriptions say so, and `compare_companies` warns when the latest dates are more than 60 days apart; the model can still ignore it.
- Agent tools (3.1): return on equity uses year-end equity (no average of the opening and closing equity), so it differs from the usual definition for fast-growing equity (NVDA FY2026: equity went from 79.3 to 157.3 billion). The revenue concept mixing of 1.5 (priority-based concepts) could distort growth for another company; AAPL and NVDA each use ONE concept for all years (checked), so it does not today.
- Agent tools (3.1): stored EPS is not split-adjusted consistently: NVDA's `eps_diluted` is 1.73 (FY2021) and 3.85 (FY2022) before the 10-for-1 split of 2024 and 0.17, 1.19, 2.94, 4.90 for FY2023 to FY2026 (each period keeps the value of its latest-filed 10-K). The `get_financials` description tells the model not to compare EPS across years; no derived metric uses EPS. Fixing it needs split data in the ingestion.
- Agent tools (3.1): price metrics exclude dividends and use the stored closes, which come from the Redis cache and can be up to `CACHE_TTL_SECONDS` (10 minutes) old. The window is `days` CALENDAR days, so `days=90` gave 63 trading days; volatility and drawdown depend on that window.
- Agent tools (3.1): the agent will call `search_filings` repeatedly, and every call costs one OpenAI embedding and, with reranking on, one Cohere call (real runs: the embedding request took 2.7 to 4.3 seconds and the rerank 1.0 to 1.4 seconds, 5.7 and 3.7 seconds per call in total). The Cohere trial key allows only 10 rerank calls a minute: above that reranking fails open (the tool still answers, with the fused order, so ranking quality drops under load). There is no per-run limit on search calls yet (3.2's step limit is the guard).
- Agent tools (3.1): the filing text returned by `search_filings` is untrusted and could contain instructions (a prompt injection inside a filing). The tool does not sanitize it; the 3.2 system prompt must treat all tool output as data, never as instructions. It also inherits the 2.1 parsing noise (page footers, flattened tables), and the same paragraph of two fiscal years can fill two of the results (real: NVDA FY2025 and FY2026 export-control paragraphs in one answer).
- Agent tools (3.1): a ToolException is returned to the caller as a plain string by a direct `tool.invoke` (because of `handle_tool_error = True`), so a caller that does not go through a `ToolNode` has to tell an error message from a result by its type (`str` against `dict`). `scripts/try_agent_tools.py` does that.
- Agent tools (3.1): `websockets` is now 16.1.1 instead of 17.2 (`langgraph-sdk` needs `<17`). It is a transitive dependency of `uvicorn[standard]`, `yfinance` and `langsmith` and is not pinned; `pip check` is clean and the full suite passes, but a future `pip install` of newer versions could move it again.
- Agent tools (3.1): the input checks (`ticker` strings, `fiscal_year_from`/`to`) are not validated against the years that exist in the data; a year with no filing simply gives an empty result with the "no relevant passage" message.
